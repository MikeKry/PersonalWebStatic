Agents, subagents, agent teams: do they pay off on an ordinary machine?

In February, Claude Code added experimental agent teams whose members message each other directly. They are often pitched as a faster option than subagents. So I measured it: three tasks, three modes, 91 valid runs on an ordinary laptop.

In February, Claude Code added an experimental feature called agent teams. Team members can message each other directly, not only through the main agent. They are often described as a faster option than subagents, especially when work can be split up.

I had run one task with an agent team myself, and it felt faster. Instead of steering a single agent and watching its output, I left the work to the team and only reviewed the result. But I had never measured it.

I also mostly work on a single computer. And within one project, running that many agents at once can be a problem.

So I measured it. Same model, same task, same computer, only a different mode.

I was hoping agent teams would come out on top and save me time again. But I knew from the documentation that they do best on a well-tuned task that splits cleanly into parts.

TL;DR: On a single machine, neither subagents nor an agent team paid off for me: in all three tasks they were more expensive and slower than one agent. On the large .NET project, the agents also hit a bottleneck: several of them tried to build the solution at the same time.

#How the modes were set up

Every mode got the same task. Only the opening paragraph of the prompt differed, the text instruction I use to hand the agent its work. In short:

ModeInstruction in the prompt
One agentDo the whole task yourself, step by step, in one session. The tool for starting other agents was also disabled.
SubagentsYou are the main agent and you coordinate the work. Give each role one subagent and pass it everything it needs. Subagents report only to you; write as little code yourself as possible.
Agent teamCreate a team and lead it. Use the shared task list and let teammates message each other directly. Wait until everyone is done, verify the result and shut the team down.

A session is one conversation with the model. A subagent gets a task, works in its own session and returns only the result. Members of an agent team (teammates) are separate sessions that can also message each other.

Subagents and the team got the same roles in each task. I split them the way I would split the work in a real team.

#V1 Kanban: split by application layer

Task: a small Kanban board from scratch in React and TypeScript, no backend. Three columns, a card limit in the Doing column, priorities, search, undo and saving to the browser. Logic must be separate from the UI, and hidden tests run against a fixed interface.

  • architect sets up the project and tooling and writes down how the parts fit together.
  • domain-dev writes the board logic (cards, priorities, undo) and its unit tests.
  • ui-dev builds the components and the app itself.
  • tester checks at the end that the app really runs and the main scenarios work.

Why this way: logic and UI can be written in parallel if the interface is agreed first. So the architect goes first and the others get a finished agreement.

#V2 OrchardCore: one developer per requirement

Task: fix issue #14810 in OrchardCore. After switching from SQLite to PostgreSQL, culture codes became case-sensitive, so a filter on en-GB found nothing. The agent had to store codes in lowercase, convert existing data and fix every place that looks things up by culture.

  • graphql-dev fixes culture filtering in GraphQL.
  • migration-dev writes a migration that converts the stored data.
  • web-dev fixes the culture picker on the website.
  • reviewer writes the release notes, runs the full build with tests and reviews the result as a whole.

Why this way: the three requirements touch different parts of the code, so the developers don't get in each other's way. But OrchardCore is a large .NET solution, and two builds over the same files block each other. So each developer builds only its own projects, and the reviewer runs the full build at the end.

#V3 Backlog: one developer per issue, an integrator at the end

Task: five OrchardCore issues I had filed myself. For each one, the agent first had to find out what was already solved, then implement the rest with tests and documentation:

  • #18455: DI and interface refactoring. Configurable culture aliases, a custom media key and replaceable Lucene services, part of it already solved.
  • #14197: taxonomies. Tell apart terms with the same name in the picker, such as "New" under both computers and phones.
  • #10539: deployment. Let data sources know that a deployment succeeded, so they can, for example, remove a "to deploy" tag.
  • #10285: deployment. A step that deletes content on the target site that was deleted on the source.
  • #9662: admin. Show which database the site is connected to without revealing the password.

Roles:

  • di-dev handles #18455, taxonomy-dev #14197 and tenants-dev #9662.
  • deployment-dev got both #10539 and #10285, because both change the same deployment modules.
  • integrator comes in after the developers finish: full build and tests, release notes, a BACKLOG.md summary and a check of the commits.

Why this way: the result had to be one branch with a commit per issue, the same as with one agent. So the developers worked at the same time in one checkout. When they hit a file locked by another agent, they were told to wait a moment and retry.

#How I measured

All runs ran on my personal laptop, one after another:

Test machine

  • Laptop: Dell XPS 15 9500
  • CPU: Intel Core i7-10750H, 6 cores / 12 threads, 2.6 GHz
  • Memory: 16 GB RAM
  • OS: Windows 11, no Docker
  • Model: Claude Sonnet in every mode
BenchmarkTaskRuns per modeHow quality is scored
V1 Kanbansmall web app from scratch14–1554 hidden tests (unit, UI, architecture)
V2 OrchardCorefixing one bug in a real CMS538 hidden tests on SQLite and PostgreSQL
V3 Backlog5 real issues: triage, implementation, tests, docs3acceptance tests, blind model review, human check

The tasks, hidden tests and scripts of all three benchmarks are on GitHub.

When you measure something you care about, it's tempting to adjust the rules to fit the result. It only takes deciding after scoring that one criterion "doesn't really make sense," and suddenly there's a different winner. So for V3 I wrote the scoring rules down in advance, the way scientific studies do.

Before the first run, I wrote down what the real problem in each issue is, how points are awarded and how a fix is verified. I committed it all to git, which records the date of every change. Anyone can check that the rules existed before the results and that I didn't bend them afterward.

V3 quality was first scored by a model (Opus), blind, twice independently and without knowing the mode. Then I scored six solutions myself, also blind. That step turned out to matter most.

Watch out for claude -p: The first runs were non-interactive (claude -p) so they could be repeated. According to the documentation, though, Claude doesn't spawn teammates in this mode, and a named agent runs as a subagent. So I reran all 23 team runs as a real agent team in an interactive session.

A script drove that interactive session. I count the team's time only up to the agents' last activity.

I had filed all five V3 issues in OrchardCore myself. So during the human check I knew right away what they were really about.

#Time and money: one agent won all three

Average per run. Cost is an estimate based on API pricing for tokens, the units of text you pay for.

Quality barely differed between modes in V1 and V2. In V1, practically every test passed in every mode. In V2, every run fixed the bug except one real-team run that got stuck.

So delegating didn't produce a better result. But it cost 1.6–3.7× more money and took 1.3–2.8× longer.

Delegating had one advantage: better tests. When a separate subagent wrote them in V2, they actually caught the bug being fixed in 5 of 5 runs. A single agent doing everything itself managed that in only 3 of 5.

In V3, every run but one delivered a working solution: the project built, nothing broke and all five tasks were done. The exception was one real-team run. The differences only showed up when checking whether a solution did what the task actually asked for.

#The real agent team: where it got stuck

In the interactive session, the team really formed. In every run it had three to five members who messaged each other. But it showed weaknesses that -p mode doesn't have:

  • A background result doesn't wake the agent. A teammate starts a build or tests in the background and waits. The result lands in the queue, but the idle agent doesn't pick it up, and the team stalls.
  • A denied permission interrupts the lead. In -p mode the model gets an error and carries on. In an interactive session the denial ends its turn, and it waits for instructions.
  • The lead reports done when it isn't. In V3, one run skipped an entire issue and wrote no summary. The lead still reported the work as finished.

So in V2, one run got stuck with a broken build, and two others sat waiting after finishing their work until the time limit. With a person at the keyboard, someone would have nudged the team along. But the point of a team is that it works on its own while you do something else.

#Limitations listed in the documentation

Agent teams are still an experimental feature. The documentation itself lists what doesn't work yet. I ran into some of it too:

  • Task status lags. Teammates sometimes don't mark a task as done, and dependent tasks stall. The documentation suggests fixing the status by hand or nudging the lead.
  • Background work may not work. A teammate can't reliably run things in the background: the request either fails or silently runs in the foreground.
  • Shutting down can take a while. Each teammate finishes its current step first.
  • No session resumption. After /resume, the teammates are gone, and the lead may message someone who no longer exists.
  • One team, a fixed lead. A session has exactly one team, the lead can't be replaced and teammates can't start their own sub-team.
  • The same permissions for everyone. Teammates start with the lead's permissions and can't be configured individually.

Most public numbers are about tokens, not quality. Here is how they compare with what I measured.

General research and my numbers point the same way. More agents help mainly where the work can truly be done in parallel. But I found no measurement of Claude Code modes with blind quality scoring and a human check.

#Do others see similar results?

Outside Anthropic, I found few hands-on measurements of teams versus subagents. Most articles are impressions and estimates, but they point the same way:

  • Tahir Nazir ran the same small task as a team and as subagents, also on Windows. The team cost about 1.7× more and never formed under claude -p, just like in my runs. It's a single run, and the author says himself it's not a benchmark.
  • Builder.io, in You Probably Don't Need Claude Agent Teams, estimates 3–4× more tokens. In their view a team is the wrong tool for a bug fix or a refactor, and they advise actively watching it. That matches my stalled runs.
  • Rahul Garg (Thoughtworks) on martinfowler.com describes four subagents on a .NET project. Working in parallel saved time, but each one reloaded the same architecture, and one ran git operations on the shared tree.
  • A counterexample: Berkeley researchers in Evolving Agent Teams show that a team of agents beats standard coding agents on the same token budget. But these aren't Claude Code agent teams: their team is run by its own supervisor that keeps restructuring it. And the task is long-running GPU kernel optimization, not everyday development work.

#Quality: the model was happier than I was

Under the rules set in advance, V3 quality scored like this, out of 50 points:

ModeModel review with human checkMy second pass: did it understand the task?
One agent46.532.2
Team via -p44.932.8
Subagents38.033.2
Real agent team35.9AI check only, see below

I had the real team scored in a new blind round together with all the earlier solutions. The earlier modes moved by at most 0.8 points from the first round, so the scoring is stable. The real team came last, with the widest spread: 26.8, 42.0 and 39.0 points.

The weakest was the run that skipped an entire issue. Without it, the team would have scored 40.5, still below one agent.

But the model gave higher scores than I did. On the six solutions I scored myself, I gave 2.4 points less on average. On two solutions, the gap was 4.5 and 5.5 points.

We agreed on triage, meaning whether the agent recognized what was already solved. We disagreed on correctness and design. The model trusted a well-written change description; I saw that the solution missed the point of the issue.

So I went through all 45 original solutions again with a single question: did the agent understand what exactly needed solving? The modes evened out at 32–33 points. One agent's lead came mostly from a better-written summary of its work, not from better code.

Take this second pass with a grain of salt, though. I scored it alone and knew which mode wrote what. So I don't build a ranking from it. It mainly shows one thing: a nice score from a model doesn't mean the agent understood what I wanted.

I ran the real team only after that, and I didn't go through its solutions by hand. I had a model check them on the two task nuances I had found while reading the earlier solutions. I describe them in the next section.

One run of three handled content deletion correctly, and none caught the HTTP 200 problem. So the team didn't understand the task any better than the other modes.

#Where it breaks: the nuances of the task

Two things that weren't written in the task decided the most points. Only someone who looked into the code knew them.

Callback after a successful deployment (#10539). The issue wanted the "to deploy" tag removed only after a successful import into production. But the remote import catches a recipe error and still returns HTTP 200.

So a callback that "runs on 200" would remove the tags even for a deployment that failed. 1 solution of 12 handled that. Four others called the callback for every step separately instead of once for the whole deployment.

A step for deleting content (#10285). The issue says there's no manual way to find out what was deleted on staging. But deletion in this CMS is soft, and deleted items stay in the index.

So they can be found automatically. 3 solutions of 12 did that; the other nine asked the user to list the IDs by hand.

The automated acceptance tests passed at 100% for all 9 original runs, including solutions that missed the point. Neither the tests nor the model as a judge caught these nuances; only a person who knows the domain did.

And the mode? Only a single run caught both hidden nuances, and it used subagents. The real team caught the soft delete in one run of three. But one run in twelve isn't a pattern.

#What this means on an ordinary machine

Parallel agents need parallel hardware. When three agents build a .NET solution at the same time on 6 cores, they fight over the CPU and over files. MSBuild then reports that a file is being used by another process.

You can see it in the run transcripts. In V2, a locked file showed up 0× for one agent, 8× for subagents and 72–74× for the teams over five runs. In V3, it was 12× for one agent and 111–165× for the delegating modes over three runs.

But the bottleneck isn't the only reason. V1 had no heavy build, and delegating still took 2.6–2.7× longer. You also pay for coordinating the agents.

I'm not alone in this. At Block, agents on one machine fought over CPU, memory and disk during Gradle builds, so they queue the builds. Separate working copies (git worktrees) help with files, but still share memory and CPU. And the agent teams documentation itself recommends one agent or subagents for sequential work and edits to the same files.

On a laptop, delegation also ran into things outside the model itself:

  • System sleep. Windows with Modern Standby put the laptop to sleep during a run despite a keep-awake lock. One run sat idle for 2.5 hours.
  • Tool permissions. In non-interactive mode, the agent was denied PowerShell. Subagents worked around it with Bash; the team via -p stopped.
  • Account limit. After four V3 runs I hit my account's spend limit and had to repeat five runs. Delegation costs more, so you hit the limit sooner.

On a 32-core server, the times would probably look different. The token cost would stay the same.

#When delegation makes sense and when it doesn't

On an ordinary machine I start with one agent and treat delegation as the exception. My measurements suggest this:

SituationWhat to chooseWhy
a typical bug or feature in one moduleone agentthe same quality in half the time at 1/2 to 1/4 of the cost
you need tests that really catch the buga subagent just for testsin V2, the subagents' tests caught the bug in 5 of 5 runs, one agent's in 3 of 5
lots of independent work that doesn't fit in one contextsubagents or a teammy tasks didn't test this; a backlog of 5 issues was still small
an issue with nuances where understanding decidesone agent plus your time on the task descriptionno mode improved this
a laptop and CPU-heavy buildsone agentparallel builds slow each other down
an unattended agent team, say overnightbetter nota background result doesn't wake an idle agent

The biggest lever isn't the mode, it's the task description. With two sentences about HTTP 200 and soft delete, I think the solutions would have been better in every mode. But I didn't test that.

#Conclusion

Does it pay off on an ordinary machine? For everyday development work, my numbers say no. One agent was the cheapest and fastest in all three tests, and I didn't measure better quality from delegation.

I keep subagents for independent tests. The real agent team was the least reliable on my tasks. I'll give it a chance only for work that truly doesn't fit in one context, and only when I'm sitting next to it.

Today an AI agent delivers clean, tested and documented code that solves a slightly different problem than the one you had. No test or other model will catch that. You will, if you know the domain.

#So what did it all cost?

In total I ran 141 runs, and 91 made it into the results. The rest were pilot runs, runs stopped by the spend limit, and reruns after bugs in my scripts or the laptop falling asleep.

At API prices, the tokens for all runs cost about $228. The blind model review added another $23, so about $251 in total. My own work with Claude Code on preparing and evaluating the benchmark isn't included.

The runs themselves took 41.5 hours in total. During V2 the laptop also fell asleep seven times, for about 13 hours in total, even though I was keeping it awake. It was the display timeout that kept putting it to sleep, and I reran the affected runs.

Eight days passed between the first and the last run, from November 14 to 22.

#What's next

The benchmark is on GitHub, so you can run it on your own machine. I'll turn the best solutions into pull requests for OrchardCore. The issues are mine, so it's time to see them through.

Next time I want to try the same issues with the nuances written in. And a task that's truly too big for one agent, where a team could show what it's for.

Do you measure only tokens for your AI agents, or also whether they understood the task?
